# M5 라운드 상태·승리·무승부 검증

상태: **사용자 검증 완료 보고.** 이탈·재접속은 PIE 외 별도 호스트/클라이언트 프로세스 실행 안내 후 완료 보고를 받았다. 아래 목록은 재검증용 절차이며, 개별 실행 로그를 수집하지 않아 항목별 체크를 일괄 변경하지 않는다. 7번의 강제 요청 경계 테스트 실행 여부는 별도 미확인이다.
빌드·에디터 작업은 사용자가 담당한다. 기존 WBP_NBChat을 그대로 사용하며 새 위젯이나 Blueprint 이벤트 연결은 필요 없다.

## 1. 이번 단계 범위

- 두 명 접속하면 시작하며 초과 접속은 거절한다.
- Waiting → Playing → ShowingResult를 GameState에 복제한다.
- 먼저 서버에서 처리된 3S는 승리, 두 명 모두 세 번 소진하고 정답자가 없으면 무승부다.
- 결과는 기존 채팅창에 표시한다. 대기/종료 시 숫자만 막고 채팅은 유지한다.
- 클라이언트가 나가면 Waiting. 다시 두 명이 되면 횟수 0, 새 정답 생성, RoundId 증가.
- 결과 전용 공지 위젯은 M6, 결과 3초 후 자동 재시작은 M7이다. **이번에는 결과 후 자동 재시작하지 않는 것이 정상이다.** 독립 시나리오마다 PIE를 다시 시작한다.

## 2. 빌드와 기본 환경

- [ ] USTRUCT/UENUM/복제 필드/RPC 인자가 변경되었으므로 에디터를 닫고 CH4_1Editor Win64 Development 빌드를 확인한다.
- [ ] 기존 L_NumberBaseball, BP_NBGameMode, BP_NBPlayerController, WBP_NBChat 설정을 유지한다.
- [ ] 기본 검증은 Number of Players 2, Play Net Mode `Play As Listen Server`, 양쪽 창을 사용한다.
- [ ] Output Log에서 `LogNB`를 확인한다. 정답은 서버 개발 로그의 `Server answer=...`이며 시작 전 1인 대기에서는 생성하지 않는다.

`Phase`: 0=Waiting, 1=Playing, 2=ShowingResult. `Result`: 0=None, 1=Win, 2=Draw.
GS 로그의 `Authority=1`은 서버, `Authority=0`은 클라이언트 상태 알림이다.
클라이언트는 빠른 중간 상태를 생략하고 최신 스냅샷을 받을 수 있다. 모든 중간 로그가 양쪽에서 같은 횟수로 나올 필요는 없다.

## 3. 시작·채팅 회귀

- [ ] 1 Player로 별도 PIE 실행: 두 명 대기 안내, 숫자 입력/버튼 비활성, 채팅 가능, 정답 생성 없음.
- [ ] PIE를 종료하고 2 Player로 시작: 양쪽에 `[R1][라운드] 라운드 시작!` 안내, 각자 `[0/3]`, 숫자 입력 가능.
- [ ] 호스트/클라이언트가 각각 일반 채팅을 보내고 양쪽에 한 번씩 보이는지 확인한다.
- [ ] `12`, `112`, `012`, `abc`, 공백 포함 숫자를 숫자창에 제출: 제출자에게만 안내, 횟수 유지.
- [ ] 유효한 오답: 양쪽에 같은 `[R1][숫자] ... [1/3]`, 제출자 횟수만 증가.

## 4. 승리

각 사례는 새 PIE로 실행하고 매번 해당 실행의 서버 정답을 읽는다. 아래에서 '오답'은 정답과 다른 유효한 세 자리 숫자다. 같은 오답을 반복해도 된다.

- [ ] 호스트가 첫 시도에 정답: 양쪽에 동일한 승자, 서버 `Phase=2 Result=1`, 호스트 `[1/3]`.
- [ ] 새 PIE에서 원격 클라이언트가 첫 시도에 정답: 양쪽에 원격 플레이어 이름으로 승리 표시.
- [ ] 새 PIE에서 A가 오답 세 번, B가 오답 두 번 후 정답: B `[3/3]`과 **B 승리**. 무승부로 바뀌지 않는다.
- [ ] 결과 이후 양쪽 숫자 입력/버튼이 잠기고, 채팅은 계속된다. 3초 이상 기다려도 승자/결과가 유지된다.
- [ ] 가능하면 양쪽이 정답을 거의 동시에 제출: 서버가 먼저 처리한 한 명만 승자이며 추가 횟수 소비나 결과 덮어쓰기가 없다.

판정 메시지는 일회성 Multicast, 라운드 결과는 복제 상태다. 네트워크 조건에서 화면의 두 문구 도착 순서를 성공 기준으로 삼지 않는다. 결과·승자·횟수가 서버 판정과 일치하는지 확인한다.

## 5. 무승부

- [ ] A만 오답 세 번: A 숫자창만 잠김, B는 계속 제출 가능, 아직 `Playing`.
- [ ] 이어서 B도 오답 세 번: 양쪽 무승부 안내, `Phase=2 Result=2`, 모두 `[3/3]`.
- [ ] 무승부 후 일반 채팅 가능, 숫자 입력 불가, 추가 승패/판정/횟수 증가 없음.

## 6. 정원·이탈·재접속

- [ ] 별도 3 Player 접속 검증: 서버가 세 번째 접속에 `server is full (2 players)` 오류를 반환하고 참가자는 두 명만 유지한다. 테스트 후 2 Player 설정으로 되돌린다.
- [ ] 진행 중 원격 클라이언트만 연결 종료: 호스트가 Waiting으로 바뀌고 숫자창 잠김. 이탈을 승리/무승부로 처리하지 않는다.
- [ ] 호스트를 유지한 채 원격 플레이어를 재접속: RoundId 증가, 양쪽 `[0/3]`, 정답 생성 로그 재출력, 숫자 입력 가능. 이름은 비어 있는 Player 번호 재사용.
- [ ] 결과 표시 중 원격 이탈도 Waiting으로 전환하고 다시 두 명이 되면 새 라운드가 시작된다.

PIE 구성에 따라 한 창을 닫으면 전체 세션이 종료되거나 추가 접속 실패로 PIE 전체가 끝날 수 있다. 그런 경우 해당 검증을 통과 처리하지 않는다. 이탈/재접속은 호스트를 유지할 수 있는 별도 클라이언트 프로세스에서 확인한다. 호스트까지 재시작해 R1이 된 경우는 재접속 검증이 아니다. 새 정답이 우연히 이전과 같을 수 있으므로 생성 로그·RoundId·횟수로 확인한다. 호스트 종료는 서버 종료이며 호스트 이전은 제공하지 않는다.

## 7. 서버 방어 경로 — 기본 UI 검증과 구분

UI가 막혀 있다는 것만으로 서버 거절 경로를 실행했다고 기록하지 않는다.

- [ ] 종료 직전에 이미 전송된 추가 요청이 서버에 도착했다면 `Rejected guess ... Phase=2`와 횟수/결과 불변을 확인한다.
- [ ] 이전 RoundId를 가진 요청을 재접속 새 라운드 이후 전달하는 별도 디버거/테스트 환경이 있다면 `SubmittedRound != CurrentRound` 거절과 횟수 불변을 확인한다.

기본 UI는 현재 RoundId를 보내므로 이전 ID를 임의로 입력할 수 없다. 재현하지 못한 두 경계 사례는 **서버 검사 정적 검토 완료, 실행 검증 미실시**로 남긴다. 검증만을 위한 우회 RPC나 제품 기능은 추가하지 않았다.
