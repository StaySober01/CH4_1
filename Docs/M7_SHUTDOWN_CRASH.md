# M7 종료 크래시 조사

사용자 보고: 결과 대기 중 클라이언트 종료 시험 후 QueuedThreadPoolWrapper.cpp:167의 Work->GetRefCount() == 0 assertion 발생.

## 확인한 증거

- Saved/Crashes/UECC-Windows-0E7DFDC645DF6F88E55064B01ADD6F6A_0000의 로그와 CrashContext 기준 엔진은 5.6.1, 실행은 원격 클라이언트 -game 프로세스다.
- 호스트 CH4_1.log: UTC 05:21:14.015 R1 무승부, 14.973 Waiting, 05:21:50.303 재접속 R2 Playing. 다음 이탈에도 05:22:03.734 Waiting을 기록했다.
- 첫 클라이언트 CH4_1_2.log는 R1 결과 직후 종료 요청 후 정상 Exiting으로 끝났다. 다만 종료 중 PathTracingMainRG RTPSO 컴파일이 약 71~89초 소요되었다.
- 크래시 클라이언트 CH4_1_3.log는 R2 Playing을 받은 뒤 종료했다. 이 로그에는 R2 ShowingResult 수신 기록이 없다. 사용자가 보고한 테스트 전체 맥락과 실제 크래시가 남은 프로세스/시점을 구분해야 한다.
- 크래시 로그 순서: 05:22:02 종료 요청 → 월드/네트워크 정리 → 05:22:03.471 Object subsystem successfully closed → 03.493 assertion. 게임 타이머 실행 위치를 가리키는 심볼 스택은 없다.
- 로컬 엔진 소스 FQueuedThreadPoolWrapper::Destroy는 예약 작업을 Retract한 뒤 ReleaseWorkNoLock을 호출한다. 해당 함수는 참조 수 0을 검사한다. LaunchEngineLoop 종료 경로에 GThreadPool->Destroy가 있다. 심볼 없는 스택만으로 정확한 작업 객체까지 특정할 수는 없다.
- 크래시 프로세스에서도 Path Tracing RTPSO 8개 컴파일 요청이 있었다. 렌더링 비동기 작업 종료와의 연관성은 가설이며 원인 확정은 아니다.

## 다음 비교 검증

1. 결과를 만들지 않고 Playing 도중 클라이언트를 닫아 같은 오류가 발생하는지 확인한다.
2. 동일 실행 명령에 -noraytracing만 추가하여 같은 종료 시험을 반복한다. UE 5.6 로컬 D3D12Adapter.cpp에서 지원을 확인했다. 프로젝트 설정을 영구 변경하지 않는 원인 분리 시험이다.
3. 계속 재현되면 해당 새 로그/크래시와 엔진 디버깅 심볼을 통한 정확한 호출 스택으로 작업 종류를 좁힌다. 단 한 번 재현되지 않은 것을 해결로 간주하지 않는다.

게임 코드/타이머 지연 변경이나 assertion 제거는 하지 않았다. M7은 사용자 검증 대기를 유지하며 종료 크래시 해결로 처리하지 않는다.

## 사용자 비교 시험 결과

- 사용자 보고: 진행 중 클라이언트 종료와 -noraytracing 적용 후 종료, 두 비교 상황에서 같은 크래시가 재현되지 않았다.
- 기본 실행에서도 재현되지 않았으므로 레이트레이싱 비활성화의 효과나 원인 관계를 확정할 수 없다. 상태는 '재현되지 않음, 원인 미확정'이며 '수정 완료'가 아니다.
- 추가 코드/엔진 설정 변경 없이 원래 실행 옵션으로 결과 3초 대기 중 이탈 및 재접속을 다시 확인한다. 재발하면 해당 실행의 로그와 크래시 자료를 비교한다. M7 전체 검증 완료 여부는 별도 사용자 확인 대기다.
- 후속 사용자 보고: 최초 크래시와 동일한 상황으로 다시 진행했으나 이번에는 크래시가 발생하지 않았다. 원래 조건에서도 미재현으로 기록한다. 원인 확정이나 수정 완료를 의미하지 않으며 추가 코드 변경은 하지 않는다. 자동 재시작·횟수 초기화 등 M7 전체 기능의 완료 보고와는 구분한다.

## 현재 처리 상태

사용자는 종료 크래시를 제외한 M7 기능 검증 완료를 보고했다. M7 기능은 완료로 기록하되 이 크래시는 원인 미확정·현재 미재현인 미해결 이슈로 유지한다. 추가 코드 변경이나 해결 판정은 하지 않았다.
