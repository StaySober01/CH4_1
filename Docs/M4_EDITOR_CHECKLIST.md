# M4 PlayerState 시도 횟수 검증

**사용자 검증 완료**. 사용자의 '검증 완료' 보고로 빌드/위젯/일반 PIE 검증을 완료 처리했다. 개별 실행 로그와 지연 조건에서 4번째 RPC를 실제 도착시킨 추가 테스트 결과는 별도 수집하지 않았다. 아래 절차는 회귀 검증에 사용한다.

## 1. 빌드 및 위젯

1. 에디터를 닫고 Development Editor / Win64 빌드한다. 새 RepNotify/Getter/BindWidget이 추가되었다.
2. WBP_NBChat의 기존 Vertical Box에 Text 위젯(UTextBlock)을 추가한다. 숫자 입력줄 위나 아래에 배치하면 된다.
3. 이름을 정확히 `AttemptsText`로 지정하고 Is Variable을 켠다. Slot은 Auto, 임시 Text는 `내 시도 횟수 [0/3]`으로 지정해도 된다. 실행 시 C++이 갱신한다.
4. 기존 ChatInput/SendButton/GuessInput/GuessButton/ChatScrollBox/ChatHistoryText는 유지한다.
5. Compile/Save한다. AttemptsText의 Text 또는 숫자 입력창의 Is Enabled에 Blueprint Binding을 별도로 만들지 않는다. C++에서 상태에 맞게 갱신한다.
6. 2 Player PIE, Listen Server + 원격 Client로 실행한다.

## 2. 최소 검증 순서

사용 횟수 표시이므로 0/3 → 1/3 → 2/3 → 3/3으로 증가한다. 최대 3번 사용할 수 있으며 '남은 기회' 표기가 아니다.

| 순서 | 동작 | 기대 결과 |
| --- | --- | --- |
| 1 | 양쪽 처음 접속 | 각자 `내 시도 횟수 [0/3]`. 잠깐 준비 중 표시가 있을 수 있으나 이후 입력 가능 |
| 2 | 호스트가 abc / 112 / 12 입력 | 호스트 오류 안내, 양쪽 자신의 횟수는 0/3 유지 |
| 3 | 호스트가 유효한 123 입력 | 호스트 1/3, 클라이언트 자신의 횟수 0/3. 양쪽 판정 메시지에 Player 1의 [1/3] |
| 4 | 클라이언트가 유효한 456 입력 | 클라이언트 1/3, 호스트는 1/3 유지. 양쪽 메시지에 Player 2의 [1/3] |
| 5 | 호스트가 같은 유효 숫자를 두 번 더 입력 | 호스트 2/3 → 3/3, 클라이언트 자신의 횟수는 그대로 |
| 6 | 호스트의 소진 상태 확인 | 숫자 입력/제출 버튼 비활성화. 채팅창과 전송 버튼은 활성 |
| 7 | 호스트가 일반 채팅창에 123 또는 문장 입력 | 정상 채팅, 횟수 3/3 유지 |
| 8 | 클라이언트가 남은 두 번 제출 | 2/3 → 3/3, 원격 UI도 잠김. 호스트는 그대로 채팅/판정 메시지 수신 |
| 9 | 두 사람 모두 일반 채팅 | 계속 대화 가능. 아직 무승부 공지/자동 리셋은 없음 |
| 10 | PIE 종료 후 재시작 | 새로운 PS의 0/3 초기 표시. 중복 위젯/알림 없이 시작 |

3S는 유효한 제출이므로 이번 M4에서도 한 번 소비한다. 승리 판정은 M5이므로 3S가 나와도 남은 기회가 있으면 계속 입력할 수 있다.

## 3. 복제와 호스트 구분

- 서버 `TryConsumeAttempt`의 LogNB에서 플레이어별 1/3, 2/3, 3/3 소비를 확인한다.
- 원격 클라이언트의 `OnRep_Attempts` 로그에서 각 플레이어 상태가 전달되는지 확인한다. 이름과 횟수는 서로 다른 프로퍼티이므로 초기 로그의 이름 표시 시점은 달라질 수 있다.
- 호스트 횟수가 바뀌는 데 클라이언트 OnRep가 필요한 것은 아니다. 서버 변경의 로컬 델리게이트가 호스트 UI를 갱신한다.
- 빠른 연속 입력에서는 상태 복제가 중간값을 생략할 수 있다. 최종 횟수 일치와 판정 메시지의 개별 [사용/최대] 값을 함께 확인한다.
- UI의 초기 상태/갱신은 PS 복제에서 읽는다. 전체 판정 메시지의 횟수를 자기 횟수로 덮어쓰면 안 된다.

## 4. 서버의 추가 입력 방어

UI 차단과 별도로 서버의 ProcessGuess와 PS의 TryConsumeAttempt가 소진 여부를 검사한다. 네트워크 지연 환경에서 원격 클라이언트가 UI 차단 전에 여러 유효 입력을 보내 서버에 4번째 요청이 도착한 경우 다음을 확인한다.

- 서버 `Rejected guess: Sender=... Attempts=3/3` 로그
- 제출자에게만 소진 안내
- 횟수는 3/3 유지, 추가 판정 메시지 없음

일반 PIE에서 UI가 먼저 잠겨 4번째 요청이 서버에 도착하지 않았다면, UI 차단 검증과 서버 초과 요청 검증을 구분하여 기록한다. 일부러 서버에 추가 요청을 보내지 못했다면 이 항목은 실행 미검증으로 남긴다. 클라이언트 입력 차단을 해제해도 서버 횟수를 바꿀 권한은 생기지 않는다.

## 5. 공유할 결과

빌드/위젯 Compile, 양쪽 0→3 표시, 플레이어별 독립 횟수, 오입력 기회 유지, 소진 후 숫자 차단·채팅 유지, 재실행 초기화 결과를 알려준다. 서버 초과 요청 테스트는 실제 요청 도착 여부도 구분한다. 실패하면 관련 LogNB와 어느 플레이어 창인지 함께 공유한다.
