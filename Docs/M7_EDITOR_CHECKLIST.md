# M7 결과 후 자동 재시작

상태: **종료 크래시를 제외하고 사용자 기능 검증 완료 보고.** 종료 크래시는 Docs/M7_SHUTDOWN_CRASH.md의 별도 미해결 이슈로 유지한다. 아래는 재검증용 절차다. 새 UMG/Blueprint 설정은 없다. 기존 결과 위젯과 채팅 위젯을 그대로 사용한다.

## 검증 절차

1. 에디터를 닫고 CH4_1Editor 빌드를 확인한다. 기존 Listen Server 호스트 + 원격 Client 2인으로 실행한다.
2. 서버 개발 로그에서 정답을 읽고 한 명이 정답을 제출한다. 양쪽 승리 공지가 표시되고 숫자 입력은 잠겨야 한다. 결과 중에도 채팅은 가능해야 한다.
3. 서버가 결과를 확정한 뒤 약 3초에 자동으로 다음 라운드가 시작되는지 확인한다. 양쪽 공지가 사라지고 각자 0/3, RoundId 증가, 숫자 입력 재개, 정답 생성 로그 재출력을 확인한다.
4. 새 정답과 다른 유효 숫자를 두 명이 각각 세 번 제출한다. 무승부 공지 후에도 같은 초기화가 이루어지는지 확인한다.
5. 승리와 무승부를 섞어 최소 세 라운드를 계속한다. RoundId가 한 번에 1씩 증가하고, 한 결과에 재시작이 두 번 발생하지 않아야 한다. 마지막 기회 3S도 승리 후 재시작해야 한다.
6. 한 플레이어가 숫자창에 제출하지 않은 문자를 남겨둔 상태에서 상대가 승리한다. 새 라운드에는 숫자창이 비워져야 한다. 일반 채팅 이력과 입력 중인 채팅은 유지한다.
7. 별도 호스트/클라이언트 프로세스에서 결과 3초가 지나기 전에 원격 클라이언트를 종료한다. 호스트가 이탈을 감지하여 Waiting이 된 후 3초 이상 기다려도 혼자 시작하면 안 된다. 재접속하면 0/3의 새 라운드가 한 번 시작되어야 한다.
8. 가능하면 결과 중 이탈/빠른 재접속 후 이전 타이머 예정 시각을 넘겨 본다. 새 라운드가 갑자기 초기화되거나 RoundId가 추가 증가하면 안 된다. 서버가 이탈을 실제 처리한 시점은 로그/Waiting 표시로 구분한다.
9. 결과 표시 중 전체 게임을 종료하고 다시 실행해도 이전 타이머가 영향을 주거나 종료 오류가 발생하지 않아야 한다.

3초는 서버 게임 시간 기준이다. 클라이언트가 결과를 받은 시각부터 정확히 3초를 보장하는 수신 확인 방식은 아니다. 지연/멈춤이 있는 환경에서 화면 표시 시간을 정밀하게 같다고 가정하지 않는다. 새 난수는 우연히 이전 정답과 같을 수 있으므로 숫자의 차이가 아닌 생성 로그와 RoundId로 확인한다.

기본 UI 차단만으로 이전 RoundId 요청의 서버 거절 경로까지 검증했다고 기록하지 않는다. 별도 요청 주입을 하지 않았다면 해당 경계 사례는 정적 검토만 완료한 것으로 남긴다.

## 변경 흐름

`FinishRound → ShowingResult 복제 → 서버 3초 단발 타이머 → ResetGame(예약 당시 RoundId) → 현재 ID/단계 검사 → StartRound → 횟수 0 / 정답 생성 / 새 RoundId와 Playing 복제 → UI 공지 숨김·숫자창 초기화·입력 복구`

- Logout과 EndPlay에서 타이머를 해제한다. 새 라운드를 시작할 때도 기존 핸들을 정리한다.
- 결과에서 다음 게임으로 전환할 때 임시 Waiting을 공개하지 않아 불필요한 대기 문구를 띄우지 않는다. 참가자가 부족하면 Waiting으로 돌아간다.
- PS와 GS 복제는 서로 다른 Actor이므로 잠깐의 표시 차이는 있을 수 있다. 서버가 상태를 결정하고 UI는 Playing과 남은 횟수를 모두 확인한다.

설명할 질문: 타이머는 왜 서버에만 필요한가? 왜 예약한 RoundId를 다시 확인하는가? 왜 정답이 이전과 다르다는 것을 검증 조건으로 삼으면 안 되는가?

## 이전 체크리스트와 달라진 점

M5/M6의 '결과가 계속 유지됨', '다음 사례는 PIE 재시작'은 당시 단계의 동작이다. M7에서는 3초 후 자동 시작과 반복 플레이를 기준으로 검증한다. 공지 표시 중 이탈 시험도 이 3초 안에 수행한다.
