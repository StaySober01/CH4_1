# M8 필수 기능 통합 검증과 설명

상태: **2026-10-08 사용자 통합 검증 완료 보고.** Codex 직접 실행 결과는 아니며 개별 로그는 별도 미수집이다. M2~M7 사용자 완료 보고는 유지하며, 아래는 최종 코드에서 여러 기능이 이어지는지 확인하는 회귀 시나리오다. 종료 크래시는 별도 미해결 이슈다.

## Codex 정적 검토 기록

| 검토 대상 | 확인 내용 |
| --- | --- |
| GM ProcessGuess | 참가자·RoundId·Playing·기회·형식 검사 후에만 소비. 3S를 무승부보다 먼저 검사 |
| 규칙 라이브러리/테스트 | ASCII 1~9 중복 금지, 계산 실패와 OUT 구분, 504개 자기 비교 및 대표 판정 사례 |
| PS / GS | 변경 함수 서버 권한 검사, DOREPLIFETIME 및 Super 호출, 호스트 직접 알림과 원격 OnRep |
| PC / 위젯 | 로컬 생성, 초기 스냅샷 조회, PS 연결 해제, 결과 표시와 채팅 중복 검사 분리 |
| 리셋 | 3초 단발 타이머, 예약 ID/단계 검사, 이탈/EndPlay 취소, 새 ID와 횟수/입력 초기화 |

이 검토는 컴파일이나 런타임 성공의 증거가 아니다. 이번 단계는 C++·에셋·설정을 바꾸지 않아 기존 사용자 빌드/계산 테스트 결과를 유지한다. 새 코드 변경이나 오류가 없다면 같은 빌드를 반복할 필요 없다.

## 하나의 2인 세션에서 확인

호스트를 A, 원격 클라이언트를 B로 두고 양쪽 화면을 함께 확인한다. 판정 재현에는 각 라운드의 서버 개발 정답 로그를 사용한다. 오답은 그 정답과 다른 유효 숫자를 선택한다.

| 순서 | 조작 | 기대 결과 | 실행 결과 |
| --- | --- | --- | --- |
| 1 | 2 Player Listen Server 시작, A/B 각각 채팅 | 두 명 시작, 각자 0/3, 양쪽 동일 메시지 1회 | 사용자 완료 보고 |
| 2 | B 숫자창에 12, 112, 012, abc 입력 | B만 오류 안내, 양쪽 횟수 불변 | 사용자 완료 보고 |
| 3 | B 유효 오답 1회, A 일반 채팅창에 123 | B만 1/3, 채팅은 기회 미소비, 양쪽 판정 일치 | 사용자 완료 보고 |
| 4 | A 정답 제출 | A 승리 공지 양쪽 표시, 숫자 잠금/채팅 가능 | 사용자 완료 보고 |
| 5 | 서버 기준 3초 대기 | 새 RoundId, 각자 0/3, 공지 숨김, 입력 재개 | 사용자 완료 보고 |
| 6 | A 오답 3회 → B 오답 2회 → B 정답 | A만 소진해도 계속, B 마지막 시도 승리, 무승부 아님 | 사용자 완료 보고 |
| 7 | 자동 재시작 후 A/B 각각 오답 3회 | 전원 소진 때만 무승부, 공지 후 재시작 | 사용자 완료 보고 |
| 8 | 새 라운드에서 양쪽 다시 제출 | 횟수 독립, 이전 결과/숫자 입력 잔존 없음, 채팅 이력 유지 | 사용자 완료 보고 |

결과 메시지와 프로퍼티 도착 순서가 화면마다 완전히 같을 필요는 없다. 각 판정 메시지의 횟수와 최종 상태가 맞는지 확인한다. Enter와 버튼을 각각 사용하여 중복 제출/포커스 이상 여부도 확인한다.

## 기존 검증을 유지하는 항목

2인 정원·이탈/재접속·결과 중 타이머 취소는 M5/M7에서 사용자 확인을 받았다. 새 문제나 코드 변경이 없다면 이번에 모두 반복할 필요는 없다. 종료 크래시는 같은 조건에서도 재현되지 않았지만 해결로 판정하지 않는다. 재발 시 해당 로그/크래시를 [조사 기록](M7_SHUTDOWN_CRASH.md)과 비교한다.

기본 UI가 막혔다고 강제 이전 ID/종료 후 서버 요청 거절까지 실행했다고 체크하지 않는다. 네트워크 지연·Dedicated Server·위젯 초기화 순서별 시험은 별도 미검증으로 유지한다.

## 코드 설명 연습

| 질문 | 설명에 포함할 내용 |
| --- | --- |
| 왜 GameMode에 정답을 두는가? | 서버에만 존재하며 최종 규칙/판정을 담당, GS로 정답 복제 안 함 |
| 클라이언트는 어떻게 서버에 요청하는가? | 소유 PC의 ServerSubmitGuess, 서버 PC의 this로 발신자 식별 |
| RPC와 Replication을 어떻게 구분했는가? | 제출/채팅은 이벤트, 횟수/결과는 현재 상태 |
| 호스트 UI는 왜 직접 갱신하는가? | C++ 서버 변경에 OnRep 자동 실행을 기대하지 않음 |
| Library가 있는데 GM도 검증하는 이유는? | Library는 순수 형식/계산, GM은 참가자/단계/기회 등 게임 권한 판단 |
| 무승부보다 승리를 먼저 확인하는 이유는? | 마지막 기회 정답도 승리이기 때문 |
| RoundId가 필요한 이유는? | 이전 라운드 요청/예약을 현재 라운드와 구분 |
| 왜 결과 후 3초를 기다리는가? | 결과 공개 시간을 두며 서버가 재시작 결정. 복제 지연 해결용 임시 Delay 아님 |
| 위젯이 늦게 만들어지면? | 생성 직후 GS/PS 현재 상태 조회, 이후 변경 알림 |
